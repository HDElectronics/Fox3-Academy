# A-10C II and CAS exterior art

Seven original Blender-authored exterior models, under the repository MIT licence. No third-party meshes,
image textures, extracted game assets, cockpit interior or weapon internals. Small fittings and store
subvariants are artist approximations; these are visual teaching aids, not engineering models.

| File | Runtime IDs | Exterior |
|---|---|---|
| `a10c.glb` | `a10c` | Straight low wing and drooped tips, two high nacelles, twin fins, bubble canopy, muzzle, gear pods, 11 empty pylons |
| `gbu12.glb` | `gbu12` | Paveway II, tail fins extended |
| `agm65.glb` | `agm65d/h/l`, `agm65` | One Maverick family body; window differences simplified |
| `apkws.glb` | `apkws` | LAU-131 seven-opening carriage pod, never a flying rocket |
| `mk82.glb` | `mk82` | Low-drag bomb exterior |
| `cbu97.glb` | `cbu97` | Closed canister |
| `tgp.glb` | `tgp` | Litening-family pod with opaque sensor windows |

The existing Vite registry bundles these files. `JetMesh('a10c')` loads its exterior and retains the
synchronous `getJetModel('a10c')` procedural fallback. This rebuild does not change any gameplay, CAS UI
or loadout attachment behavior. `AgStoreVisual` still keeps procedural geometry for flying APKWS rockets.

## Blender authoring and rebuild

The source follows the same family layout and two-step Blender export/preparation pipeline as the fleet:

- Jet: `scripts/assets/source/aircraft/a10c/create_a10c.py`.
- Six stores: `scripts/assets/source/stores/generate_stores.py`, alongside the existing stores.
- Shared mesh/export and Cycles studio helpers: `scripts/assets/source/blender_exterior.py`.
- Orchestration: `scripts/assets/rebuild_models.py` and `scripts/assets/prepare_models.py`.

All seven are Blender-authored, using `bpy`/`bmesh` and Blender's glTF exporter. Python automates Blender;
it is not a standalone GLB writer. OpenVSP was not used for these models. The layout alignment preserves
the approved geometry, materials, component names, modifiers and export settings without redesigning them.
The unchanged recipes were moved to their aircraft/store families; common helpers avoid duplicating their
mesh and studio code.

```sh
python3 scripts/assets/rebuild_models.py \
  --blender /Applications/Blender.app/Contents/MacOS/Blender \
  --work /private/tmp/fox3-a10-aligned \
  --only a10c gbu12 agm65 apkws mk82 cbu97 tgp
```

For a comparison rebuild that leaves the application GLBs untouched, add
`--out /private/tmp/fox3-a10-aligned/models`. Omitting `--out` writes the production assets.

Each generator writes `<out>/<id>/model.glb`, `model.blend`, review PNGs and a source `manifest.json`.
With the command above, the jet files are under `/private/tmp/fox3-a10-aligned/aircraft/a10c/a10c/`;
stores are under `/private/tmp/fox3-a10-aligned/stores/<id>/`. Source manifests identify the generator as
`../create_a10c.py` or `../generate_stores.py`, matching the other families' relative-path convention.
The wrapper copies review GLBs into its `review/<id>/` tree and runs the standard preparation step.

The production manifest uses the same nine fields for every asset: `id`, `category`, `name`,
`source_sha256`, `sha256`, `bytes`, `references`, `source_caveats`, and `authorship`.
Authoring/version/axis details stay in source-review metadata and this document. The preparation step
retains all nine A-10 hinge roots and the `partNames` scene extras needed by the existing runtime tests.

## Review capability

As with the other generators, a normal rebuild renders the model in Cycles and saves an editable studio
scene. The A-10 includes `front.png`, `side.png`, `top.png`, `quarter.png`, `rear.png` and `deployed.png`;
the six stores include the first four. Open `model.blend` to inspect or rerender the saved studio.
Direct generator invocations also accept `--no-render` when only an export and source scene are needed.

The separate shipped-GLB review script was removed because the other families have no separate review
runner. To inspect an optimized export, import `src/assets/models/<id>.glb` into Blender or use the existing
browser gallery. Existing independent Cycles export-review images remain local evidence from the original
Blender rebuild; their paths are recorded below. Generated `.blend` files, renders and comparison exports
remain local review artifacts; the Python generators are the preferred source.

## Axes and moving parts

Recipe coordinates are metres, nose -Z, up +Y, right +X. Geometry is explicitly converted to Blender's
+Y forward / +Z up before authoring; normal glTF export converts back to the runtime axes. The requested
jet envelope is 16.26 m long and 17.53 m wide. No runtime scale or coordinate contract changes are needed.

`a10Rig.ts` continues to bind these existing names:

- `gear.nose`, `gear.port`, `gear.starboard`
- `flap.port`, `flap.starboard`
- `deceleron.port.upper/lower`, `deceleron.starboard.upper/lower`

Gear geometry is authored down and baked into its retracted pose about each hinge. The existing runtime
rotation restores wheel contact at Y = -1.95 m when gear is fully deployed. Flaps lower; deceleron halves
open in opposite directions. All nine pivots are required before configured states use the GLB. Failed
or incomplete loads retain the procedural fallback. Hinge travel is a drawing convention; gear doors,
canopy opening and aileron roll are not animated.

## Visual references and limits

The [A-10 three-view](https://commons.wikimedia.org/wiki/File:Fairchild_Republic_A-10_Thunderbolt_II_3-view.svg)
was inspected for the wing, nacelle, fuselage and tail silhouette. It is a family reference, not exact
C II equipment certification. The [DCS A-10C II page](https://www.digitalcombatsimulator.com/en/products/planes/tank_killer/)
provides variant identity. Reference imagery is not redistributed or used as a texture. Store proportions
remain simplified external representations; Maverick D/H/L deliberately share one shell.

Review checks include orthographic front, side and top views, front/rear quarters, deployed parts and
store views. GLB audits check structure, finite positions, embedded resources, bounds and geometry budgets.
Render tests check catalogue aliases, orientation, 11 pylon labels, seven pod openings, rig deployment and
retraction, incomplete-rig fallback, pre-load configuration and the carriage-pod/projectile distinction.
Physical-device performance, exact variant fidelity and LOD chains remain outside this review.

The jet is 17.5300 m wide and 16.2591 m long in its clean configuration. Runtime axes remain metres,
nose −Z, up +Y, right +X. All nine existing pivots, eleven pylon labels and seven APKWS pod-opening
labels survive export and preparation. No runtime wiring or test edits were needed.

The original Blender rebuild added curved wing sections, smoother fuselage/canopy/gear-pod shells, beveled surface edges,
nacelle/rudder seams and a canopy frame projected onto the glass. The first Cycles review exposed a
floating windshield bow; it was corrected and the A-10 source and production GLB rebuilt before final checks.
Material batching and indexed Blender exports keep file sizes small despite the higher triangle counts.
The independent export review also exposed a preview-only Euler/quaternion mismatch after Blender import;
the Cycles studio now applies hinge rotations as quaternions and restores the original transform.
The production rig and its passing runtime tests needed no changes.

## Source-layout alignment validation

The alignment rebuild used the command above with `--out /private/tmp/fox3-a10-aligned/models`.
All seven rebuilt production GLBs were **byte-for-byte identical** to the approved models already in
`src/assets/models/`; their review-source SHA-256 hashes were also identical. The shipped GLB files were
not overwritten and no hash changes were necessary. All 51 unrelated manifest records remain unchanged.
Every production entry now has exactly the standard nine fields. Geometry recipes and existing store
builder functions were also compared structurally to confirm the move introduced no modelling edits.

Checks passed: `npx tsc --noEmit -p .` (zero errors), `npx vitest run src/render` (188 tests),
`npm run build`, and `npm test` (1651 passed, 4 skipped). No runtime wiring or test paths needed changes.
No Git commands were run.
